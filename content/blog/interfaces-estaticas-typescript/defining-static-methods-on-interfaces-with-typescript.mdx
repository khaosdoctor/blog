Yesterday I was putting together the classes for [Formação TS](https://formacaots.com.br) and I ran into something pretty interesting, something I've been racking my brain over for years myself (yesterday included).

When we talk about object-oriented programming, one of the hardest things to understand is the concept of static properties versus instance properties, and this gets especially tricky when we try to type a dynamic language on top of a static type system.

I won't go into detail about what static or non-static methods are in this article, because there's plenty of other content out there that goes into far more detail than I can here.

But it's worth a quick refresher.

## Static methods

Static methods, or static attributes, are attributes that exist on every instance of a class. They're defined at the constructor level, meaning the class itself owns these methods, and so every instance of that class owns them too.

A common static method shows up when you're building a domain object, or a database entity, for example:

```ts
class Person {
  static fromObject (obj: Record<string, unknown>) {
    const instance = new Person()
    instance.prop = obj.prop
    return instance
  }

  toObject () {
    return {
     prop: this.prop
    }
}
```

The `fromObject` method exists on every class. It sits above any instance, so it can't use the `this` keyword, because `this` [hasn't been initialized yet](https://twitter.com/_StaticVoid/status/1708966256487911727), and also because you're in a context above any instance that `this` could point to.

In this case we're taking an object and creating a new instance of the class straight from it. To run this code, instead of doing something standard like:

```ts
const p = new Person()
p.fromObject(etc) // error, the property doesn't exist on the instance
```

We need to call the method directly on the class's constructor:

```ts
const p = Person.fromObject(etc)
```

## The problem

Static methods are very common in strongly typed languages, because you have a clear separation between the class's static moment and its "dynamic" moment.

But what happens when we need to type a dynamic language with a static type system?

In TypeScript we run into errors when we try to declare, for example, that a class has both dynamic and static methods and try to describe both in a single interface:

```ts
interface Serializable {
  fromObject (obj: Record<string, unknown>): Person
  toObject (): Record<string, unknown>
}

class Person implements Serializable 
// Class 'Person' incorrectly implements interface 'Serializable'.
// Property 'fromObject' is missing in type 'Person' but required in type
// 'Serializable'.
```

This happens because interfaces in TypeScript operate on the class's "[dynamic side](https://www.typescriptlang.org/docs/handbook/interfaces.html#difference-between-the-static-and-instance-sides-of-classes)", so it's as if every interface were an instance of that class, never the class itself.

Luckily, TypeScript has a way to declare a class as a constructor, the so-called **Constructor Signatures**:

```ts
interface Serializable {
  new(...args: any[]): any
  fromObject (obj: Record<string, unknown>): Person
  toObject (): Record<string, unknown>
}
```

That should do it, right? Unfortunately not, because even if you implement the method by hand, the class will still say you haven't implemented the `fromObject` method.

## The static reflection problem

And the problem goes further. Say we wanted to build a database class that grabs the entity's name straight from the class to create a file. That's done through the `name` property on any class, a static property that exists on every instantiable object:

```ts
interface Serializable {
  toObject (): any
}

class DB {
  constructor (entity: Serializable) {
    const path = entity.name // name doesn't exist on the property
  }
}
```

Ok, so we can swap `entity.name` for `entity.constructor.name`, which works, but what about when we need to create a new entity from an object?

```ts
interface Serializable {
  toObject (): any
}

class DB {

  #entity: Serializable
  constructor (entity: Serializable) {
    const path = entity.constructor.name
    this.#entity = entity
  }

  readFromFile () {
    // read from the file here
    const object = 'conteúdo do arquivo como um objeto'
    return this.#entity.fromObject(object) // fromObject doesn't exist
  }

}
```

So we're stuck with a choice: either we prioritize the instance or we prioritize the constructor...

## The solution

Luckily, there's a solution to this problem. It's not pretty, but there are some ideas in the TypeScript repository (like [this one](https://github.com/microsoft/TypeScript/issues/33892) and [this one](https://github.com/microsoft/TypeScript/issues/34516)), going back [to 2017](https://github.com/microsoft/TypeScript/issues/13462), looking at the possibility of adding static definitions to interfaces.

But until that idea arrives, what we've got is the interface split into two parts: the static part and the instance part:

```ts
export interface SerializableStatic {
  new (...args: any[]): any
  fromObject(data: Record<string, unknown>): InstanceType<this>
}

export interface Serializable {
  id: string
  toJSON(): string
}
```

> It's important to note that the constructor in `new(...args: any[]): any` **has to** be typed as `any` on the return, otherwise it turns into a circular reference

With both parts of the class typed, we can say the class only implements the instance part:

```ts
class Person implements Serializable {
  // ...
}
```

Now, we can say our database will take two type parameters: one will be the static part, which we'll call `S`, and the other will be the dynamic (or instance) part, which we'll call `I`. `S` will always extend `SerializableStatic` and `I` will always extend `Serializable`, defaulting to the type of an instance of `S`, which we can get with the `InstanceType<S>` type utility:

```ts
class Database<S extends SerializableStatic, I extends Serializable = InstanceType<S>> { }
```

Now we can have our properties as usual, for example:

```ts
class Database<S extends SerializableStatic, I extends Serializable = InstanceType<S>> {
  #dbPath: string
  #data: Map<string, I> = new Map()
  #entity: S

  constructor(entity: S) {
    this.#dbPath = resolve(dirname(import.meta.url), `.data/${entity.name.toLowerCase()}.json`)
    this.#entity = entity
    this.#initialize()
  }
}
```

And in our `#initialize` method we'll use the `fromObject` method to read straight from the file and turn it into a class instance:

```ts
class Database<S extends SerializableStatic, I extends Serializable = InstanceType<S>> {
  #dbPath: string
  #data: Map<string, I> = new Map()
  #entity: S

  constructor(entity: S) {
    this.#dbPath = resolve(dirname(import.meta.url), `.data/${entity.name.toLowerCase()}.json`)
    this.#entity = entity
    this.#initialize()
  }

  #initialize() {
    if (existsSync(this.#dbPath)) {
      const data: [string, Record<string, unknown>][] = JSON.parse(readFileSync(this.#dbPath, 'utf-8'))
      for (const [key, value] of data) {
        this.#data.set(key, this.#entity.fromObject(value))
      }
      return
    }
    this.#updateFile()
  }
}
```

Meanwhile we can have methods like `get` and `getAll`, or even `save`, that only take and return instances.

```ts
get(id: string): I | undefined {
  return this.#data.get(id)
}

getAll(): I[] {
  return [...this.#data.values()]
}

save(entity: I): this {
  this.#data.set(entity.id, entity)
  return this.#updateFile()
}
```

Now, when we use a database like this:

```ts
class Person implements Serializable {
  // code here
}

const db = new DB(Person)
const todas = db.getAll() // Person[]
const umaOuNenhuma = db.get(1) // Person | undefined
db.save(new Person()) // DB<Person>
```
