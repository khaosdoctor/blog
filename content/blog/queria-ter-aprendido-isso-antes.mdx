Uma das principais lições que eu aprendi ao longo da minha carreira, é que  
software não é construído somente em uma única tacada. Não é como se você  
escrevesse o código do seu próximo produto uma única vez e nunca mais encostasse nele.

Código _evolui_, ele precisa ser **mantido**.

Então para cada linha de código que você escreve, você tem uma linha de código a  
mais que você deve manter ao longo do tempo.

Por isso é super importante a capacidade de reutilizar o código, de quebrar e  
reorganizar funcionalidades em módulos, e é justamente isso que eu quero falar  
pra você hoje.

Quando estamos construindo APIs, é muito comum que façamos várias checagens de erros em todos os lugares, ou até mesmo tenhamos várias partes do código onde  
estamos lançando erros a todo momento e temos que tratar em cada um desses  
lugares. Isso tem vários problemas:

-   É difícil manter um padrão de mensagem, porque os erros estão sendo lançados  
    em todos os lugares
-   Alterar uma mensagem de erro pode significar múltiplos arquivos alterados
-   Mudanças simples acabam se tornando complexas porque seu código está espalhado  
    em todo lugar

Por isso eu gosto de adotar duas práticas, a primeira é lançar erros que  
contenham toda a informação necessária para a resposta da minha requisição, por  
exemplo:

```ts
class HTTPError extends Error {
    constructor (message: string, readonly status: number = 500, cause?: Error) {
        super(message)
        this.name = HTTPError.name
    }
}
```

Veja que nosso `HTTPError` possui tudo que é necessário para que retornemos a  
mensagem para o cliente, que é o código HTTP do erro e, se necessário, uma  
causa. Inclusive, podemos até separar o erro em vários erros específicos, como  
um `NotFoundError` e etc.

Agora, usando a arquitetura de middlewares, podemos criar um único  
middleware de tratamento de erros que irá receber todos esses erros e tratá-los  
com base na resposta:

```ts
export function ErrorHandler (err: Error, _req: Request, res: Response, next: NextFunction)
{
    switch (true) {
        case err instanceof HTTPError: {
            return res.status(err.status).json({ message: err.message })
        }
        case err instanceof ZodError: {
            return res.status(422).json({ message: err.message, issues:
                err.issues })
        }
        default: {
            return res.status(500).json({ message: err.message, code:
                'UNKNOWN_ERROR' })
        }
    }
}
```

Dessa forma, podemos lançar erros em **qualquer** lugar da nossa aplicação que  
iremos capturar usando nosso middleware, basta que chamemos o `next(err)`.
