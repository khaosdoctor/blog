# Two languages, one codebase

Portuguese is the source language and lives at the root. English is a translation tree under `/en/`. This file is the
machinery: what pairs a post with its translation, what the guard enforces, what it deliberately leaves alone, and
what a third language would cost.

`docs/architecture.md` explains the content model, `docs/translation-voice.md` covers how translations are written.
Neither is repeated here.

## The rules the code encodes

| Rule | Where |
|---|---|
| The list of languages | `LOCALES` in `src/i18n/ui.ts` |
| Which one is the source | `SOURCE_LOCALE` in `src/i18n/ui.ts`, `SOURCE_LANG` in `src/lib/posts.ts` |
| What a language is called to a crawler | `HREFLANG` in `src/i18n/ui.ts` |
| Where a shared route lives per language | `localePath()` in `src/i18n/ui.ts` |
| Which language a page is in | its own directory under `src/pages/`, and `localeFromPath()` for MDX components |
| Which language a post is in | the `lang` frontmatter key, nothing else |
| Which posts are translations of each other | the folder they share |
| Every string the chrome shows | the `ui` tables in `src/i18n/ui.ts`, read through `t(locale, key)` |

The source language keeps the bare path (`/error-cause/`), every other language is prefixed (`/en/what-is-error-cause/`).
That is one rule, written once in `localePath()` and again in `urlOf()` for posts.

## Which routes exist in which language

`scripts/check-i18n.ts` holds the table, and a new route under `src/pages/` fails the check until it is classified.

- **per-locale**: the home page, the post page, the section index, the markdown twin, the feed, the manifest, search.
  Every language needs its own copy.
- **shared**: `404`, `offline`, `robots.txt`, `link-metadata.json`, `scheduled.json`. The first two carry both
  languages on one page, because a static host serves one 404 for the whole domain and the service worker serves one
  offline page for any uncached URL. The rest carry no prose.
- **source-only**: `llms.txt`, `/series/<name>/`, `/tags/<tag>/`. See the limitations below.

## What the guard checks

`node scripts/check-i18n.ts`, wired into `npm run check`. It reads source, never build output, so it runs before a
build exists. It fails the build on:

1. A `ui` key that is blank in any language, or missing from one table, or present in a translation table and not in
   the source one.
2. A translated string identical to the source string, which is a key somebody copied and never filled in. Words that
   genuinely read the same in every language live in `LANGUAGE_NEUTRAL_KEYS`.
3. `%d`/`%s` placeholders that differ between languages for one key, which silently drops or reorders an argument.
4. A language with no `HREFLANG` value, or two languages claiming one value.
5. `SOURCE_LANG` in `src/lib/posts.ts` disagreeing with `SOURCE_LOCALE` in `src/i18n/ui.ts`.
6. Copy duplicated into a build-time `.mjs` plugin drifting from the key it mirrors, or missing a language.
   Two of those exist (`NOT_WRITTEN_YET`, `FOOTNOTES_LABEL`), both because a `.mjs` plugin cannot import the module.
7. A route under `src/pages/` that is not classified, a per-locale route with no copy for some language, or a route
   that exists under `/en/` with no source-language counterpart.
8. A page calling `t()` with a language other than the tree it renders in.
9. A component or layout calling `t()` with a literal language at all: those render in every tree, so the locale has
   to arrive as a prop or from the path.
10. User-visible text written straight into markup (`aria-label`, `alt`, `placeholder`, `title`), where `t()` can
    never reach it. Brand names live in `LANGUAGE_NEUTRAL_TEXT`.
11. A file holding one case per language that has no case for one of them, listed in `LOCALE_AWARE_FILES`. Files that
    handle languages generically are deliberately absent from that list.
12. Content: a post whose `lang` is not a known language, two files in one folder claiming the same language, two
    published posts resolving to one URL, or a folder whose `index` file is not in the source language.

It warns, without failing, on a draft folder whose index is not in the source language. There are twelve of those
today and they are explained below.

## What it deliberately does not check

- **Translation quality.** Whether a sentence reads well, matches its original, or uses the right word is not
  something a script can judge, and a checker that guesses gets ignored.
- **Link targets.** It reads source, so it cannot tell that an `href` resolves to a real page. `check-output.ts` and
  the dev server are where that gets caught.
- **hreflang correctness per page.** Whether a specific page emitted the right set of alternates needs rendered HTML.
  Spot-check with `curl -s http://localhost:4321/<path> | grep hreflang`.
- **Whether every `ui` key is used.** A dead key costs nothing and chasing them produces noise.
- **Prose inside markup slots.** Text between tags, rather than in an attribute, is not scanned: almost all of it is
  already an expression, and the ones that are not are wordmarks.

## Known limitations, none of them accidental

**English has no tag index and no series index.** `/tags/<tag>/` and `/series/<name>/` are built from Portuguese posts
only. Nothing in the English tree links to either, so no reader falls out of their language today: the English post
page shows no tag chips and no series navigation. `SeriesToc` only links its heading when the page is in the source
language, so wiring it into an English page cannot produce a Portuguese link by accident. Adding these means an
`src/pages/en/series/[name].astro` and `src/pages/en/tags/[tag].astro`, both built from `getPublishedPosts('en')`,
plus the tag chips and the series block in `src/pages/en/[...slug].astro`.

**`llms.txt` lists Portuguese posts only.** The English markdown twins exist at `/en/<slug>/index.md` and the file's
own claim that any post URL takes `index.md` is now true, but the index itself is one language. Whether an agent
index should carry both is an editorial call, not a defect.

**Twelve folders hold an English `index.mdx` with no Portuguese source.** They are opinion pieces written in English
first, and they are all drafts. Publishing one breaks two things that assume the folder name is a Portuguese URL:
`scripts/check-output.ts` looks for `dist/<folder>/index.html` and fails with "missing page", and
`src/pages/scheduled.json.ts` filters on `SOURCE_LANG`, so a scheduled one never reaches the manifest the worker
polls and never publishes. `check-i18n.ts` warns about them for exactly this reason. The fix is for `check-output.ts`
to compute each folder's expected page from the index file's `lang` and `slug` (the same rule `urlFor()` in
`src/lib/post-dates.mjs` already implements) and for `scheduled.json.ts` to drop the `lang === SOURCE_LANG` filter in
favour of one entry per folder.

**Two rehype plugins write English labels into every page.**
`src/plugins/rehype-heading-anchors.mjs:39` emits `'aria-label': 'link to this section'` and
`src/plugins/rehype-math-copy.mjs:250` emits `'aria-label': 'copy formula as text'`, so a Portuguese reader on a
screen reader hears English on every heading. The fix is the pattern `FOOTNOTES_LABEL` already uses in
`src/plugins/rehype-footnote-sidenotes.mjs`: a small table keyed by locale, read through the page's own
`file.data.astro.frontmatter.lang`, with the copy added to `src/i18n/ui.ts` and the table registered in
`MIRRORED_TABLES` in the checker. The checker does not scan `src/plugins/` for hardcoded text today, because a
literal in a plugin is only wrong once there is a key to compare it against.

**The sitemap carries no `xhtml:link` alternates.** `@astrojs/sitemap` takes an `i18n` option that emits them;
`astro.config.mjs` does not set it. The `hreflang` links in each page's `<head>` are what search engines read today,
so this is a second signal missing rather than a wrong one.

**`formatDate` falls back to Portuguese.** `src/lib/posts.ts` maps `en` to `en-GB` and everything else to `pt-BR`. A
third language formats its dates in Brazilian Portuguese until that line grows a case, which is why the file is in
`LOCALE_AWARE_FILES`.

**The redirect stubs are Portuguese.** `src/integrations/redirect-stubs.mjs` writes `<html lang="pt">` and a
Portuguese sentence into every stub. Every redirect in `src/data/redirects.ts` points at a Portuguese URL, so this is
correct by construction rather than by accident; a stub for an `/en/` URL would need the copy chosen from the target
path.

## Adding a third language

Say Spanish, `es`. In order:

1. Add `'es'` to `LOCALES` in `src/i18n/ui.ts` and write the `es` table. TypeScript will not compile until every key
   is there, which is the point.
2. Add `es: 'es'` (or `es-ES`, whichever region you want crawlers to match) to `HREFLANG` in the same file.
3. Run `node scripts/check-i18n.ts`. It now names every file that has a case per language and no case for Spanish.
   Work through them: the date format in `src/lib/posts.ts`, `OG_LOCALES` in `src/lib/seo.ts`, the manifest fields in
   `src/lib/manifest.ts`, `localeFromFile` in `src/plugins/rehype-footnote-sidenotes.mjs`, and the switcher entry in
   `src/components/LangSwitcher.astro`.
4. Add the Spanish copy to the two mirrored tables the checker also names: `NOT_WRITTEN_YET` in
   `src/plugins/remark-wikilinks.mjs` and `FOOTNOTES_LABEL` in `src/plugins/rehype-footnote-sidenotes.mjs`.
5. Copy every route the table marks per-locale into `src/pages/es/`: `index.astro`, `[...slug].astro`,
   `[...slug]/index.md.ts`, `[category]/index.astro`, `rss.xml.ts`, `manifest.webmanifest.ts`, `search.astro`. Each
   one is its English twin with the locale changed; the checker fails until all seven exist.
6. Add `/es/search/` to `CHROME_PATHS` in `src/pages/robots.txt.ts`.
7. Extend `src/pages/404.astro` and `src/pages/offline.astro`, which say everything in every language on one page.
8. Add `es` to the `lang` enum in `src/content.config.ts`, and to the language list the translation workflow drives
   (`.github/workflows/translate.yml`, `scripts/translate.ts`).
9. Write the translations: `content/blog/<folder>/<spanish-slug>.mdx` with `lang: es`, beside the Portuguese
   `index.mdx`. Nothing else pairs them.
10. Run `npm run check`, then a build, then `node scripts/check-output.ts`.

Steps 1 to 4 are the ones that would otherwise fail silently. That is what the guard is for.
